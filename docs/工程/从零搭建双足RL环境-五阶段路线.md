## 阶段一　模型：MJCF 是这件事的地基

### 1.1 三条来源路径

| 路径          | 工具                 | 适用                   | 代价            |
| ----------- | ------------------ | -------------------- | ------------- |
| CAD → MJCF  | `onshape-to-robot` | 有 Onshape 设计（鸭子就是这条） | 需处理材质/质量覆盖    |
| URDF → MJCF | `mujoco` 自带转换 + 手改 | 已有 URDF（ROS 项目常见）    | 转换后必须手改执行器与碰撞 |
| 手写 MJCF     | 纯文本                | 简单机构、教学              | 复杂机器人不现实      |

鸭子走第一条：Onshape 里按零件标材质，导出 URDF/MJCF，**质量用切片软件（Cura/PrusaSlicer）算出的实际打印重量覆盖**——因为 3D 打印件是带填充率的，名义密度算出来的质量会偏大。

### 1.2 必须核对的八项（漏一项后面全歪）

| # | 项目        | 怎么查                                                 | 错了会怎样                              |
| - | --------- | --------------------------------------------------- | ---------------------------------- |
| 1 | 总质量       | `mj_model.body_mass.sum()`，与实物称重对比                  | 步频、支撑力矩全错                          |
| 2 | 各连杆惯量     | 由几何+质量自动算，确认没用手填的瞎值                                 | 摆动不受控                              |
| 3 | 关节轴方向与符号  | 在 viewer 里拖 `qpos` 滑块逐关节看                           | **左右镜像关节常反**，鸭子 `hip_pitch` 就是左负右正 |
| 4 | 关节限位      | `mj_model.jnt_range`，对着实物手动掰一遍                      | 策略学到"超出物理可达"的姿态                    |
| 5 | 初始姿态      | 关键帧 `keyframe`，鸭子是**蹲姿**不是站姿                        | 一 reset 就弹飞或穿地                     |
| 6 | 足底碰撞几何    | 看是否用简化 box/capsule 而非网格                             | 网格碰撞慢十倍还可能穿模                       |
| 7 | 执行器参数     | kp / damping / frictionloss / armature / forcerange | **sim2real 的头号杀手**                 |
| 8 | 传感器与 site | IMU site 位置、足底 site、需要读的 sensor                     | 观测与真机对不上                           |

第 7 项展开：位置伺服的执行器在 MJCF 里长这样，五个参数一个都不能瞎填：

```xml
<actuator>
  <position name="left_knee" joint="left_knee" kp="30"
            damping="0.5" frictionloss="0.05" armature="0.01"
            forcerange="-3 3" ctrlrange="-1.5 2.5"/>
</actuator>
```

- `kp`：位置增益，决定"多硬"
- `damping`：关节阻尼，真机里由舵机固件+机械摩擦提供（所以真机 PD 里 Kd 可以是 0）
- `frictionloss`：静摩擦，小舵机死区大，这一项影响很大
- `armature`：电机转子惯量折算到关节侧，**不加会让仿真里的关节"太轻太快"**
- `forcerange`：舵机扭矩上限，真实小舵机只有 2~3 N·m

来源两条：① 用 **BAM** 做辨识（鸭子用的是 `Rhoban/bam/params/feetech_sts3215_7_4V`）；② 手动扫参——固定其他参数，只调 `armature` 与 `damping`，让"自由摆动衰减曲线"和实物视频对上。

### 1.3 三个验收动作

```bash
# ① 能不能加载、总质量对不对
uv run python -c "
import mujoco
m = mujoco.MjModel.from_xml_path('你的.xml')
print('mass', m.body_mass.sum(), 'nu', m.nu, 'nq', m.nq)
"

# ② 自由落体：从 10 cm 落下，看是否穿地、是否弹跳异常
uv run python -m mujoco.viewer --mjcf 你的.xml
```

第三个是自己的土办法但也最有效：**把躯干用 `equality` 固定在空中，让腿自然下垂**，看静止角度是否与实物一致。垂不下去说明摩擦/阻尼太大，抖个不停说明 kp 太大或 armature 太小。

## 阶段二　MDP：真正决定"能不能学会"的地方

### 2.1 时间尺度（先定死，别边训边改）

| 参数               | 值             | 说明                         |
| ---------------- | ------------- | -------------------------- |
| `sim_dt`         | 0.002 s       | 物理步长 500 Hz（够稳，太大会数值爆炸）    |
| `ctrl_dt`        | 0.02 s        | 策略 50 Hz，`n_substeps = 10` |
| `episode_length` | 20 s = 1000 步 | 太短学不会周期步态                  |

**比例关系要背下来**：策略 50 Hz、物理 500 Hz~1 kHz。上层慢、下层快，中间靠子步进衔接。

### 2.2 观测：从 51 维起，别一上来 101 维

> **最终实现是 53 维**——在下面的 51 维基础上补了 `[sin(Δyaw), cos(Δyaw)]` 两维。
> 原因是 51 维对「朝向」是盲的：`gravity` 绕 z 轴旋转完全不变，`gyro` 只给瞬时值，
> 策略看不见自己偏了多少，走十几秒就会累积成掉头。详见《施工日志》第 3 轮。
> 下面按 51 维讲，是为了让「每一维为什么在这」更清楚。

| 分量 | 维度 | 累计 | 为什么需要 |
|---|---|---|---|
| 角速度 gyro | 3 | 3 | 判断"我正在往哪边倒" |
| 重力方向（或加速度） | 3 | 6 | 判断"我歪了多少" |
| 速度指令 cmd | 3 | 9 | 前后、左右、转向 |
| 关节位置 q | 14 | 23 | 当前姿态 |
| 关节速度 qd | 14 | 37 | 摆动趋势 |
| 上一帧动作 a\_{t-1} | 14 | **51** | 让策略知道"我刚在干嘛" |
| 步态相位 sin/cos | 2 | 53 | 步态时钟（**本项目 v1 不加**，见下） |

**维度是 51，不是 48**（这里原先写错了）。算法：`3+3+3+14+14+14 = 51`。别把这行算错——`OBS_SIZE` 和实际拼接长度不一致时，训练能跑但策略永远学不好。

**关于步态相位（`sin/cos` 两维）——v1 刻意不加**，理由三条：

1. **它不是传感器，是程序生成的时钟**。加进去等于给策略发节拍器，学步态更快，但**步频会被时钟锁死**，将来想让它自己找更优节奏反而受限。
2. 先让策略从物理信号（关节速度、角速度、重力方向）里自己学出交替步态，是更好的基线。学出来之后再加相位做对照实验，就能量化"这一维值多少分"。
3. 加它有代价：`OBS_SIZE` 变 53、部署端必须能生成稳定相位时钟（真机与仿真相位要对齐），契约复杂度上升。

**什么时候必须加**：如果训出来是"双足同跳"或"原地蹭着走"——说明它没抓到左右交替的节奏，这时补相位是最快的解法。

**新手最容易漏的是 `a_{t-1}`**。少了它，策略对自己的输出没有记忆，学出来的动作抖且不连贯。鸭子的 101 维里光历史动作就占了 42 维（last/2/3 + motor_targets），说明这项很关键。

**顺序必须冻结**：写成一个常量列表，训练和部署共用同一份，任何改动都算破坏契约。本项目实现在 `duck_rl/constants.py::OBS_LAYOUT`。

### 2.3 动作：位置目标，必须带缩放和限幅

```python
ctrl = default_dof_pos + action * action_scale   # action_scale 取 0.2~0.3
ctrl = jp.clip(ctrl, ctrl_low, ctrl_high)
```

- `action_scale` 太小（0.05）→ 策略学不到大幅度动作，走不起来
- 太大（1.0）→ 一训练就抽风、容易摔
- **不自带缩放是最常见的第一个 bug**：网络输出 [-1,1]，你不缩放它，关节只会在零位附近微动

### 2.4 奖励：七项就够，每项都要能说出"不加会怎样"

| 项                     | 作用      | 不加的后果   |   |   |
| --------------------- | ------- | ------- | - | - |
| 线速度跟踪 \`exp(-v-v*²)\` | 主目标     | 它不知道要走  |   |   |
| 角速度跟踪                 | 转向      | 只会直线冲   |   |   |
| 躯干竖直（重力投影）            | 别歪      | 学会侧躺蹭   |   |   |
| 高度维持                  | 别蹲着爬    | 学会贴地滑行  |   |   |
| 足底抬高/腾空时间             | 迈步而不是蹭  | 拖着脚走    |   |   |
| 关节扭矩/加速度惩罚            | 省电、动作平滑 | 高频抖动骗奖励 |   |   |
| 终止惩罚                  | 别摔      | 摔了也无所谓  |   |   |

三个铁律：

1. **每项都配权重**，先 1.0 起，看曲线再调，别一次改三项
2. **主目标权重要远大于辅助项**（10:1 量级），否则策略去优化"站得稳"而不是"走"
3. `exp(-误差²)` 形式比线性误差好训，梯度在接近目标时更细腻

### 2.4.1 奖励不是"对错"，是"打分"——一次 step 的具体算例

先破除一个误解：**奖励不是扣分制，也没有"正确动作"这个概念**。每一步环境只回一个标量，策略的唯一目标是把"从现在到回合结束的奖励总和"做大。

用鸭子的真实参数算一步（`cmd=(0.3, 0, 0)`，正在正常前进）：

| 奖励项 | 公式 | 术语值 | 权重 | 贡献 |
|---|---|---|---|---|
| 线速度跟踪 | `exp(-‖v−v*‖²/0.25)` | 0.997 | 1.5 | **1.495** |
| 角速度跟踪 | `exp(-(ωz−ωz*)²/0.25)` | 0.990 | 0.8 | **0.792** |
| 躯干竖直 | `exp(-(g_z+1)²/0.05)` | 0.992 | 0.5 | **0.496** |
| 高度维持 | `exp(-(z−z*)²/0.01)` | 1.000 | 0.5 | **0.500** |
| 活着 | 常数 1 | 1.000 | 1.0 | **1.000** |
| 动作平滑 | `Σ(a−a_prev)²` | 0.020 | −0.01 | −0.0002 |
| 扭矩 | `Στ²` | 3.5 | −0.0002 | −0.0007 |
| **合计** | | | | **≈ 4.28** |

三个反直觉点：

1. **用 `exp(-误差²)` 而不是 `-误差`**。误差 0 时得 1.0，误差大时平滑趋 0，永远不会变成大负数。好处：策略不会为了"止损"做出极端动作。
2. **两项惩罚的权重小到几乎不起作用**（−0.0007 / 4.28）。它们的作用不是"扣分"，而是**在两组都能拿到高分的方案里选更平滑的那个**，属于打破平局。
3. **"活着"每步白给 1.0**，占单步总分的 23%。这是最容易写歪的一项（见下面的对比）。

### 2.4.2 三种行为的实际得分对比

| 行为 | 单步奖励 | 回合能否跑满 1000 步 | 回合总分 |
|---|---|---|---|
| 站着不动（v=0，指令 0.3） | ≈ 3.83 | 能 | **≈ 3830** |
| 正常前进（v=0.28） | ≈ 4.28 | 能 | **≈ 4280** |
| 走两步摔（z 掉到 0.08） | ≈ 3.09 | **不能，回合终止** | 只拿到几百 |

这张表是调参的全部直觉来源：

- "走着"比"站着"每步只多 **0.45 分（12%）**，但**摔倒会终止回合**，直接损失后面所有分
- 所以如果 `alive` 权重给太大、`tracking` 给太小，策略会发现"站着最划算"——这正是新手最常见的失败模式：**训练曲线很漂亮，鸭子原地不动**
- 反过来，`tracking` 权重给到 10 倍，策略会为了追速度冒险，摔得更多

**摔倒的惩罚不是扣分，而是"未来归零"。** 这一条最反直觉：环境从不说"你摔了扣 100 分"，它只是 `done=True`，之后这个回合不再有奖励。策略是被"少赚"逼着学会不摔，而不是被"罚款"吓住。

### 2.4.3 重心与奖励是什么关系

**重心不直接进奖励。** 没有哪一项写"质心必须在支撑多边形内"，因为那需要解算支撑多边形，太重也太难训。实际做法是用两个**代理指标**间接约束：

| 代理指标 | 奖励项 | 与重心的关系 |
|---|---|---|
| 浮基高度 `qpos[2]` | 高度维持 | 质心高度 ≈ 浮基高度 + 0.044 m（本项目实测），所以压住高度就等于压住质心高度 |
| 重力在机体系投影 `g_z` | 躯干竖直 | 躯干歪了质心就偏出支撑面，这一项在它发生前就惩罚 |
| 速度跟踪 | 线/角速度 | 质心真的在移动才拿得到分，坐着不动永远拿不满 |

本项目实测质心偏后 2.6 cm，意味着：**站着时必须略微前倾**才能让质心落在足底支撑区。如果奖励里没有"竖直 + 高度"这两项，策略会学会往后坐着（依靠足底后缘支撑），看起来"没摔"，但完全走不起来。

### 2.5 终止条件与域随机化

终止：躯干高度 < 阈值（如站立高度的 60%）、pitch/roll 超过 ±40°、非有限值。

域随机化（先做前四项，够用）：

| 随机化                 | 范围                     | 为什么         |
| ------------------- | ---------------------- | ----------- |
| 地面摩擦                | 0.4~1.2                | 真机地面未知      |
| 连杆质量                | ±10%                   | 打印公差、装配差异   |
| 执行器强度 kp/forcerange | ±15%                   | 舵机个体差异、电压下降 |
| 观测噪声                | gyro/acc ±0.05，q ±0.01 | 传感器噪声       |
| 控制延迟                | 0~20 ms                | 总线延迟（进阶）    |
| 外部推力                | 每 5 s 随机推一把            | 抗扰（进阶）      |

## 阶段三　接入训练：一个类就够了

框架只要求你实现 6 个东西（`mjx_env.MjxEnv` 的抽象方法）：`reset`、`step`、`xml_path`、`action_size`、`mj_model`、`mjx_model`。骨架：

```python
import jax, jax.numpy as jp
import mujoco, mujoco.mjx as mjx
from mujoco_playground._src import mjx_env
from ml_collections import config_dict


def default_config():
    c = config_dict.ConfigDict()
    c.sim_dt = 0.002
    c.ctrl_dt = 0.02
    c.action_scale = 0.25
    return c


class MyDuck(mjx_env.MjxEnv):
    def __init__(self, config=None, config_overrides=None):
        super().__init__(config or default_config(), config_overrides)
        self._xml = "path/to/duck.xml"
        self._mj_model = mujoco.MjModel.from_xml_path(self._xml)
        self._mjx_model = mjx.put_model(self._mj_model)   # 上 GPU
        self._default_dof = jp.array([...])               # 蹲姿关键帧的关节角

    # --- 6 个必须实现的东西 ---
    @property
    def xml_path(self):    return self._xml
    @property
    def mj_model(self):    return self._mj_model
    @property
    def mjx_model(self):   return self._mjx_model
    @property
    def action_size(self): return self._mj_model.nu

    def reset(self, rng):
        data = mjx_env.make_data(
            self._mjx_model,
            qpos=jp.concatenate([jp.array([0, 0, 0.25, 1, 0, 0, 0]), self._default_dof]),
            ctrl=self._default_dof,
        )
        data = mjx.forward(self._mjx_model, data)
        obs = self._get_obs(data, self._default_dof)
        return mjx_env.State(
            data=data, obs=obs, reward=jp.zeros(()), done=jp.zeros(()),
            metrics={}, info={"rng": rng},
        )

    def step(self, state, action):
        ctrl = jp.clip(self._default_dof + action * self._config.action_scale, -1.5, 2.5)
        data = mjx_env.step(self._mjx_model, state.data, ctrl, self.n_substeps)
        obs = self._get_obs(data, ctrl)
        reward = self._get_reward(state.data, data, action)
        done = self._get_termination(data)
        return state.replace(data=data, obs=obs, reward=reward, done=done)
```

三个已经踩过的坑写在代码注释外：

1. `mjx_env.step(model, data, ctrl, n_substeps)` 内部就是 `jax.lax.scan(mjx.step)`，**不要自己在 Python 里写 for 循环**，那样无法 jit、无法并行
2. `reset` 里必须 `mjx.forward` 一次，否则 site/sensor 位置是零，观测全错
3. `State` 是 `flax.struct` 的 dataclass，改字段用 `state.replace(...)`，不能原地赋值

训练调用（Brax PPO）：

```python
from brax.training.agents.ppo import train as ppo
from mujoco_playground import wrapper

train_fn = ppo.train  # + 超参 dict
_, params, _ = train_fn(
    environment=env, eval_env=env,
    wrap_env_fn=wrapper.wrap_for_brax_training,   # 这层负责 batch/vmap
)
```

`num_envs` 是**显存的主要消耗项**：6 GB 起手 1024，12 GB 可以 4096，24 GB 才谈 8192。

## 阶段四　导出 ONNX 与"逐位对齐"

导出本身不难（`tf2onnx` 或 `torch.onnx`），难的是**对齐**。必须做这件事：

```python
# 同一份 obs，JAX 与 onnxruntime 各算一次，比 max|差|
assert np.max(np.abs(jax_out - ort_out)) < 1e-4
```

常见不对齐的三个原因：

| 原因               | 表现         | 对策                           |
| ---------------- | ---------- | ---------------------------- |
| 观测归一化没烘进图        | 输出整体偏一个常数倍 | 把 `(obs-mean)/std` 作为图的前两个算子 |
| 观测顺序不同           | 输出完全乱      | 顺序写成常量列表，两边共用                |
| 少了 `tanh` 或 clip | 输出幅度不对     | 部署侧补，或导出时带上                  |

**存下来的不只模型，还有一份"契约表"**：obs 各段含义、维度、顺序、归一化常数、动作缩放、控制频率。真机代码照这张表写，不照模型写。

## 坑位清单（按踩坑概率排序）

1. **action 没缩放** → 关节只微动，怎么训都不走
2. **joint 轴符号搞反**（左右镜像） → 一条腿往前一条往后，原地打转
3. **初始姿态用站姿而非蹲姿** → reset 瞬间弹飞 / 穿地
4. **`reset` 没 `mjx.forward`** → 观测全是 0，训练 reward 不动
5. **奖励主目标权重不够大** → 学会站着不动（reward 不为负就满足）
6. **忘记 `a_{t-1}`** → 动作抖、不成步态
7. **`sim_dt` 太大（>0.005）** → 接触数值爆炸，训练出 NaN
8. **在 `/mnt/` 上跑** → IO 慢十倍，看着像训练卡住
9. **忘记域随机化** → 仿真里走得漂亮，真机第一步就摔
10. **归一化没烘进 ONNX** → 回放动作幅度整体偏小或偏大

### 两个土办法，抓 80% 的错

1. **歪躯干测观测**：手动把 `qpos` 的四元数改成倾斜 30°，看 `gravity` 三分量是否按预期变化（竖直应 ≈ `(0,0,-1)`）。符号错、坐标系错，这一步就露馅。
2. **零动作测仿真**：`action` 全 0（即下发默认姿态），鸭子应该"站不住、慢慢塌"，`height` 单调下降。如果它悬空不动，说明执行器没接上或 kp 为 0。
